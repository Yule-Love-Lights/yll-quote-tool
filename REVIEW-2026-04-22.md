## CRITICAL

### C1. Renders bucket is effectively public — anon can read every artifact, including source customer photos

**Files:** `migrations/2026-04-22-renders-fix-rls.sql:28-29`, `src/lib/rendering/storage.ts:103-108`

`CREATE POLICY "anon read renders bucket" ON storage.objects FOR SELECT USING (bucket_id = 'renders')` grants `SELECT` to **every role that can hit the REST API with the anon key** — which is anyone on the internet. The bucket was intentionally created private (`renders-table.sql:57` sets `public = false`) so the app uses `createSignedUrl()`, but signed URLs are only meaningful when the bucket's underlying policy *denies* unsigned access. With this policy in place, any attacker who can guess a path (`{uuid}/source.jpg` — UUID v4 is 122 bits, but the UUID is also returned in the `renders` table, which itself is readable below) can bypass the signing entirely via `{SUPABASE_URL}/storage/v1/object/public/renders/{id}/source.jpg`.

Worst case: customer daytime house photos (with addresses in EXIF often, certainly identifiable from the street) + the AI composite + the rendered night scene are all browsable once the row ID leaks.

**Row IDs will leak** because of C2 below.

**Fix:** replace the blanket `FOR SELECT USING (bucket_id = 'renders')` with one of:
- Scope to the service role only and switch `storage.ts` to use a service-role client server-side (recommended for private proposal artifacts).
- Or, keep anon writes but drop anon reads entirely; `createSignedUrl` works against private buckets using the service role internally on the Supabase side.

```sql
DROP POLICY IF EXISTS "anon read renders bucket" ON storage.objects;
-- No SELECT policy for anon at all; signed URLs still resolve via supabase's signer.
```

Also the storage-bucket policies don't scope `INSERT/UPDATE/DELETE` to authenticated requests — an anonymous attacker with the URL of this Supabase project can wipe every render. See C3.

### C2. `renders` table policy exposes every row (including `failed` rows with raw error messages + internal cost data) to anyone with the anon key

**File:** `migrations/2026-04-22-renders-fix-rls.sql:13-14`

```sql
CREATE POLICY "anon full access renders" ON renders FOR ALL USING (true) WITH CHECK (true);
```

The fix comment says "matches existing table behavior" — but **that's not true**. Look at `db/schema.sql`:
- `quotes`: `alter table quotes disable row level security;` (line 13)
- `photo_corrections`: `alter table photo_corrections disable row level security;` (line 42)
- `training_houses`: `alter table training_houses disable row level security;` (line 87)

Existing tables have RLS **disabled**, which in Supabase's model still limits access to the PostgREST boundary + the anon key, but the exposure here is slightly different: `renders` explicitly enables RLS in migration 1 and then grants `FOR ALL USING (true)` in migration 2. Functionally the result is the same permissiveness — anyone with the anon JWT can SELECT/INSERT/UPDATE/DELETE any render row — but the *customer-visible* render workflow needs rows to be selectively public (`status='approved'`), not everything-public.

Concretely, once Phase 5 publishes a proposal URL, `GET /rest/v1/renders?select=*` through the anon key returns every `failed`/`rejected` render with:
- `error_message` (could contain Gemini API response bodies, internal paths, stack fragments)
- `gemini_cost_usd` (monthly spend disclosure)
- `notes` (Naldo's internal notes — "Jason's house test")
- `photo_hash` / `vision_hash` → enables cache-key brute force

**Fix:** keep the original split but *also* allow anon writes because the app writes with the anon key:
```sql
DROP POLICY IF EXISTS "anon full access renders" ON renders;
CREATE POLICY "anon read approved" ON renders FOR SELECT USING (status = 'approved');
CREATE POLICY "anon write" ON renders FOR INSERT WITH CHECK (true);
CREATE POLICY "anon update own row" ON renders FOR UPDATE USING (true) WITH CHECK (true);
-- delete can stay admin-only; the admin UI deletes through the API route.
```

Longer term: move all writes behind a service-role key kept server-side, then this table can stay read-only for anon entirely.

### C3. `DELETE /api/renders/[id]` has no auth — anyone can destroy any render and its artifacts

**File:** `src/app/api/renders/[id]/route.ts:53-65`

`deleteRender()` both nukes the DB row and purges the entire `{renderId}/*` folder from storage. There is no auth on the route, no CSRF check, no rate limit. Combined with C2 (row IDs are enumerable via the `GET /api/renders` list), anyone on the internet can:

```bash
curl -X DELETE https://app.example.com/api/renders/{uuid}
```

...and wipe Naldo's entire render gallery one ID at a time. Same applies to `PATCH` — anyone can approve or reject anything.

**Fix (minimum):**
1. Put a shared-secret header check at the top of `PATCH`/`DELETE` (`process.env.ADMIN_SECRET`) and require clients to send `x-admin-secret`. Update the admin UI to send it.
2. Rate-limit these routes (`limit: 10, windowMs: 60_000`) so even with the secret guessed, brute-force is capped.

This applies to `DELETE /api/corrections/[id]` and `DELETE /api/training/[id]` too — same no-auth shape, pre-existing, but not a Phase 1 regression. Call out as a broader issue.

### C4. Orchestrator cache lookup treats `findByCacheKey` failures as permanent cache hits, locking out retries after a DB blip

**File:** `src/lib/rendering/orchestrator.ts:47-48` → `src/lib/rendering/storage.ts:35-48`

Not the cache lookup itself, but the interaction: if a prior render reached `status='ready'` and was then manually rejected or its storage paths were deleted outside the app, the next call returns the stale `StoredRender` row with null `final_path`. The orchestrator returns it verbatim (line 48) without sanity-checking that `final_path` still exists or that the signed URL would resolve. The `/admin/renders/new` UI then redirects to `/admin/renders` and the user sees a broken "ready" card with no final image.

**Repro:**
1. Generate a render → status=ready, final_path set.
2. In Supabase storage UI, delete `{id}/final.png`.
3. Submit the same photo+vision+style again.
4. `findByCacheKey` returns the row; orchestrator skips Gemini; UI shows a broken `<img>`.

**Fix:** in `findByCacheKey`, also gate on `final_path IS NOT NULL`, OR have the orchestrator HEAD the signed URL before returning. The cheap path:
```ts
.eq('cache_key', cacheKey)
.in('status', ['ready', 'approved'])
.not('final_path', 'is', null)
```

## HIGH

### H1. Budget check is bypassed on every cache hit — a malicious retry loop can still hammer storage writes but never revalidates spend

Minor in isolation, but the comment in `orchestrator.ts:51-59` promises the budget check "fires BEFORE the render row is created so we don't leave half-written rows in the DB when over budget." That's only true for *first* calls. Because `findByCacheKey` short-circuits on line 48, a cached render returns even after the budget is blown, which is correct (we're not billing). But if an attacker is feeding slightly-varied input (so the hash differs each time) you'll get a new row every call, and *also* a budget check per call — but the budget check queries EVERY render row from the start of the month *on every POST*. With a few thousand rows that's a multi-second query for each render request. Not fatal, but puts your `POST /api/renders` latency at the mercy of Supabase index usage.

**Fix:** add a server-side cached value:
```ts
let mtdCache: { usd: number; until: number } | null = null;
export async function getMonthToDateSpendUsd() {
  if (mtdCache && mtdCache.until > Date.now()) return mtdCache.usd;
  // ... existing query ...
  mtdCache = { usd: sum, until: Date.now() + 60_000 };
  return sum;
}
```
60-second TTL keeps the window tight enough that one Gemini call ($0.20) can't sneak through multiple requests — worst case you overshoot by `RENDER_BUDGET_MONTHLY_USD + $0.20*parallelism`.

Also: `parseFloat(process.env.RENDER_BUDGET_MONTHLY_USD ?? '200')` returns `NaN` if someone sets `RENDER_BUDGET_MONTHLY_USD=off` or any non-numeric. `NaN >= NaN` is false, so the limit is silently ignored. Guard:
```ts
const parsed = parseFloat(process.env.RENDER_BUDGET_MONTHLY_USD ?? '200');
const budgetLimit = Number.isFinite(parsed) && parsed > 0 ? parsed : 200;
```

### H2. Race: a failed Gemini call between `status='rendering'` and the `catch` leaves an unrecoverable row if `updateRender` itself fails

**File:** `src/lib/rendering/orchestrator.ts:85-127`

The catch block does `updateRender(..., { status: 'failed', error_message }).catch(() => {})` — swallowing the update failure (correct — we don't want to mask the real error). But if Supabase is down (or the anon key is rotated mid-request), the row stays in `status='rendering'` forever and the `pending`/`rendering` indexes get polluted with zombie rows. The admin UI shows them as "rendering" indefinitely.

**Fix:** add a cleanup endpoint or a scheduled task that flips rows stuck in `rendering` for >10 minutes to `failed`. Simplest:
```ts
// At the top of runRender() before doing anything:
await sb.from('renders').update({ status: 'failed', error_message: 'Timed out or orphaned' })
  .in('status', ['pending', 'rendering'])
  .lt('created_at', new Date(Date.now() - 15*60_000).toISOString());
```
Slightly crude — but it prevents the zombie set from growing unbounded without needing cron.

### H3. `sharp` SVG rasterization of unsanitized vision data — XSS/SVG injection into the composite if Claude ever returns a crafted label

**File:** `src/lib/rendering/compositor.ts:223-270`, `src/lib/rendering/compositor.ts:231-233` and `:256-264`

`buildBulbSvg` and `buildMaskSvg` interpolate `{p.x}`, `{p.y}`, `{diameter}`, `{color}` directly into SVG strings. `p.x`/`p.y` come from `seg.points` in the vision payload, which comes from the POST body. `.toFixed(1)` coerces to string but if a caller ever passes a non-number (say, `NaN` or `Infinity` from a polyline point) you get `"NaN"` in the SVG, which renders nothing but might crash sharp's SVG parser. More importantly, nothing validates that `vision.santasLines[i].points[j][0]` is a finite number in `[0, 1]`.

**Repro:**
```bash
curl -X POST /api/renders -d '{
  "photoBase64":"...", "photoMediaType":"image/jpeg",
  "vision": { "santasLines": [{ "points": [["\"/><script>alert(1)</script><circle cx=\"", 0]], "label": "x" }],
    "gingerbreadLines":[], "miniLights":[], "wreaths":[], "spritzers":[], "garland":[] },
  "style":"warm-white"
}'
```
`((x as number) * width).toFixed(1)` — if `x` is a string, multiplication coerces to NaN, and `.toFixed(1)` returns `"NaN"`. Not an XSS (toFixed on NaN is safe), **but** if you ever relax that (e.g. use `x.toString()` instead of `.toFixed(1)`), injection becomes trivial. And sharp will happily rasterize arbitrary SVG — including loading remote hrefs via `<image xlink:href>` unless you explicitly disable it.

**Fix:**
1. Add a `coerceVision(v)` that validates every coord is `Number.isFinite` and clamps to `[0, 1]`. Drop segments that fail.
2. Pass `{ failOnError: true }` to sharp's SVG input and consider `sharp(svgBuf, { unlimited: false })` to cap memory.
3. In `/api/renders/route.ts:53-61`, replace the `?? []` ladder with a validated-shape coercion instead of pass-through.

Example helper:
```ts
function sanitizeLines(lines: unknown): LineSegment[] {
  if (!Array.isArray(lines)) return [];
  return lines.flatMap(l => {
    if (!l || typeof l !== 'object') return [];
    const pts = (l as any).points;
    if (!Array.isArray(pts)) return [];
    const clean: [number, number][] = [];
    for (const p of pts) {
      if (!Array.isArray(p) || p.length < 2) continue;
      const [x, y] = p;
      if (!Number.isFinite(x) || !Number.isFinite(y)) continue;
      clean.push([Math.max(0, Math.min(1, x)), Math.max(0, Math.min(1, y))]);
    }
    if (clean.length < 2) return [];
    return [{ points: clean, label: String((l as any).label ?? '') }];
  });
}
```

### H4. `/api/renders` POST body has no size cap — 100MB photo base64 accepted by Next.js App Router defaults, then JSON-parsed into memory AND re-base64'd for Gemini

**File:** `src/app/api/renders/route.ts:21-64`

Unlike `/api/analyze-photo` which has `MAX_SIZE_BYTES = 10MB` (line 12), the renders endpoint does:
```ts
const body = await req.json();
```
with no prior byte-length check. Next 16's App Router JSON parser defaults are generous. A single 50MB base64-encoded photo multiplied by concurrent requests will OOM the serverless function. Worse, on Vercel the `maxDuration = 120` means a slow attacker can hold 120 seconds of memory per request.

**Fix:**
```ts
const MAX_BYTES = 15 * 1024 * 1024;
const len = Number(req.headers.get('content-length') ?? 0);
if (len > MAX_BYTES) {
  return NextResponse.json({ error: 'Payload too large' }, { status: 413 });
}
```
And validate the decoded buffer length after base64 decode (below).

Additionally, there's no check that `photoBase64` actually decodes to a valid image. If `Buffer.from("garbage", 'base64')` produces a tiny empty buffer, sharp will throw with a confusing metadata error (line 44 of compositor.ts throws "Source photo has no dimensions — bad upload?"), but the orchestrator has already created a DB row and uploaded the garbage buffer to storage. Move the sharp-metadata validation upstream of `createRenderRow`:

```ts
// orchestrator.ts, BEFORE createRenderRow
try {
  const probe = await sharp(sourceBuf).metadata();
  if (!probe.width || !probe.height) throw new Error('not an image');
} catch {
  throw new RenderError('photoBase64 does not decode to a valid image', 'compositor');
}
```

### H5. `quoteId` is inserted verbatim into `renders.quote_id uuid` — a malformed string from the client crashes the insert with a confusing Postgres error

Also strip `stack` from the 500 response (see L4).

## MEDIUM

### M1. `samplePolyline` has an off-by-one that drops the final bulb on short runs and double-counts on looping paths

**File:** `src/lib/rendering/compositor.ts:146-167`

The `leftover` handoff between segments is clever but brittle. Consider a polyline with segments of length `(15, 15, 15)` and `spacing=18`:
- Segment 1: start `t=18`, `t<=15` false → no bulbs. `leftover = 15 - (18 - 18) = 15`? No wait — after the while loop `t=18`, which is `>15`, loop never ran. `leftover = segLen - (t - spacing) = 15 - 0 = 15`. OK.
- Segment 2: `t = spacing - leftover = 3`; loop places at 3, 21. 21>15 stops. 1 bulb. `leftover = 15 - (21 - 18) = 12`.
- Segment 3: `t = 6`; places at 6. 6+18=24>15 stop. 1 bulb. `leftover = 15 - (24-18) = 9`.
- Total arc length 45, spacing 18 → expected ~3 bulbs. Got 2. Off by one.

Also when `segLen === 0` (duplicate vertex), the code `continue`s without updating leftover, so duplicate vertices effectively reset the spacing. Minor, but vision output with accidental duplicate points will create visible bulb clumps.

**Fix:** compute total polyline arc length first, then `numBulbs = Math.max(2, Math.round(totalLen / spacing))` and interpolate N evenly-spaced points. Cleaner, predictable, and handles looped/closed polylines.

### M2. `sampleWrap` with `style='trunk'` produces three parallel vertical stripes at column centers — not what `trunk` means

**File:** `src/lib/rendering/compositor.ts:180-191`

The comment says "Three vertical columns of bulbs down the center" which matches the code, but semantically `trunk` wrap on a large tree should be a helix. Three stripes look fine on a column, but on a 20-foot tree you get three straight vertical lines instead of a spiral. Gemini may fight this placement. Low impact because the mask is a guide not a hard constraint, but composite/mask disagreement will confuse the model.

**Fix:** render an actual helix using parametric math:
```ts
const turns = Math.max(3, Math.floor(h / 48)); // roughly one turn per 4 ft
for (let i = 0; i <= steps; i++) {
  const t = i / steps;
  const angle = t * turns * 2 * Math.PI;
  const px = cx + Math.cos(angle) * (w * 0.3);
  const py = y + t * h;
  pts.push([px, py]);
}
```

### M3. `sampleCircle` draws a ring of bulbs around the *outside* of the wreath bounding box, not along the wreath itself

**File:** `src/lib/rendering/compositor.ts:206-215`

```ts
const r = Math.max(bw * width, bh * height) / 2;
```
Uses `Math.max` of width/height, so on a non-square box you get a ring that overshoots one axis. Also the radius is half the *longer* side, so the ring sits outside the actual wreath for any slightly-squished box. Should be `Math.min(...)` or better, `(bw + bh) / 4 * width`.

**Fix:**
```ts
const r = Math.min(bw * width, bh * height) / 2;
```
Also worth offsetting r by ~0.9 so the bulbs sit *on* the wreath edge rather than at maximum radius. Visual polish, not correctness, but it's cheap.

### M7. Rate limiter keyed off first `x-forwarded-for` value — spoofable, no `x-vercel-forwarded-for` fallback

**File:** `src/lib/rateLimit.ts:18-23`

On Vercel, the *trusted* header is `x-vercel-forwarded-for` (Vercel strips/overwrites `x-forwarded-for` only in specific configs). Elsewhere (Render, self-hosted) an attacker can trivially spoof `x-forwarded-for: 1.2.3.4` and bypass the limit by rotating the prefix. Non-issue locally; real concern in prod once this app is exposed publicly.

**Fix:**
```ts
function getIp(req: NextRequest): string {
  return req.headers.get('x-vercel-forwarded-for')
    ?? req.headers.get('x-real-ip')
    ?? req.headers.get('x-forwarded-for')?.split(',')[0]?.trim()
    ?? 'unknown';
}
```
Also: the `'unknown'` fallback means all un-headered clients share one bucket (fine for honest local dev, but one attacker with no headers = DoS for all other no-header clients). Acceptable tradeoff.
