# Jobber pipeline audit — 2026-07-01 (trial-blocker findings)

## Confirmed bugs
### B1. [HIGH/broken-step] changes_requested → resend is a dead-end: /send short-circuits on quote_sent_at and never re-messages the customer or moves status back to sent
- **File:** src/app/api/quotes/[id]/send/route.ts:151-159
- **Evidence:** After request-changes sets status='changes_requested', quote_sent_at is still non-null. pipelineActions() (src/lib/pipeline/pipelineActions.ts:55-57) offers Send actions for changes_requested, and both PipelineActionsMenu.tsx:9-14 and admin/quotes/page.tsx:137 POST /send with no ?retryGhl. In /send, isGhlRetry requires ?retryGhl, so `if (quote.quote_sent_at && !isGhlRetry)` returns {alreadySent:true} at line 152 — no SMS/email, no status write. updateQuote() (src/lib/quotes.ts:202-240) does NOT reset status or clear quote_sent_at when staff edit in the builder. There is no other resend endpoint.
- **Impact:** During the Aug–Oct trial, any customer who clicks 'Request changes' puts the quote in a state staff cannot get out of via the UI: staff edit + re-send does nothing (customer is never told the quote was revised, GHL card never re-advances, status stays changes_requested forever). The documented loop ('staff edit → resend', request-changes/route.ts:3-4) is non-functional.
- **Fix:** Make /send treat a changes_requested quote as a re-send: when derived/persisted status is 'changes_requested' (or when quote_sent_at is set but status !== 'sent'/'viewed'/'approved'/'booked'), re-stamp status='sent', re-run messaging, and advance the GHL card, instead of short-circuiting on quote_sent_at. Alternatively reset status→'sent' (or clear the changes flag) in updateQuote when the current status is changes_requested so the normal send path re-fires.

### B2. [HIGH/bug] Customer /approve has no status gate — a declined or cancelled quote can be re-approved (terminal states not enforced)
- **File:** src/app/api/quotes/[id]/approve/route.ts:339-351,503-515
- **Evidence:** The customer approve route never calls canTransition/deriveStatus. Its only guard is customer_approved_at (idempotency + the atomic .is('customer_approved_at', null) claim). /decline writes status='declined'+decline_reason but leaves customer_approved_at NULL (decline/route.ts:139); /cancel similarly. So a customer who declined can POST /approve again: the .is('customer_approved_at', null) predicate still matches, the write overwrites status='approved', and booking proceeds. Contrast staff-approve/route.ts:91-98 which DOES gate with canTransition(from,'approved'). quoteStatus.ts:125-127 marks declined/cancelled/lost as terminal (empty transition arrays), but customer approve bypasses that table entirely.
- **Impact:** A customer (or anyone with the portal UUID) can silently un-decline / un-cancel a dead quote and re-book it. Staff who declined a deal on the customer's behalf, or cancelled it, see it reappear as approved/booked with a real deposit charge — a state the status machine explicitly forbids and the two approval paths disagree on.
- **Fix:** In /approve, after loading the row, derive the current status and reject when !canTransition(current,'approved') (mirror staff-approve/route.ts:91-98), and tighten the atomic write predicate to also exclude terminal states (e.g. .not('status','in','(declined,cancelled,lost)')) so a concurrent decline/cancel can't be raced past.

### B3. [HIGH/bug] Tax-override on an already-paid invoice resurrects a bogus balance and un-pays it (balance is recomputed as total − deposit only, ignoring the collected balance)
- **File:** src/lib/invoices.ts:532-559 (setInvoiceTaxOverride); reachable via src/app/admin/invoices/[id]/page.tsx:200-207 (button only disabled when 'cancelled')
- **Evidence:** setInvoiceTaxOverride recomputes via computeInvoiceTotals(pricing, invoice.deposit_applied, {...}) → balance = max(0, total − deposit_applied). `deposit_applied` only ever holds the 50% DEPOSIT — it is never incremented when the balance is later collected (verified: the webhook balance path at valor/webhook/route.ts:506-517 and markInvoicePaidManually at invoices.ts:481-486 both set balance=0 without touching deposit_applied). So for a fully-PAID invoice (balance collected via pay-link/mark-paid), re-pricing yields a large positive balance again. reconciledStatus then maps status 'paid' → 'awaiting_payment' (invoices.ts:538-539) and the paid_at clear at line 557-559 wipes the payment timestamp. The admin button (page.tsx:203 disabled={busy || inv.status === 'cancelled'}) is enabled on a paid invoice, so this is reachable.
- **Impact:** An operator marking a customer tax-exempt on a legitimately fully-paid order flips the invoice back to 'awaiting_payment' showing e.g. ~$2,053 still owed (full total minus tax minus only the deposit) and erases paid_at. The customer is then dunned / a pay-link is offered for money already collected, and the AR view is corrupted. A tax EXEMPTION should only ever reduce what is owed — it must never resurrect a settled invoice.
- **Fix:** Track amount actually collected separately from the deposit (e.g. an `amount_paid` column, or bump deposit_applied on every settle), and compute balance = max(0, total − amount_paid). Minimum viable guard: in setInvoiceTaxOverride, if invoice.status === 'paid', never move it off 'paid' — an exemption on a paid invoice yields a credit_note (overpayment), never a reopened balance.

### B4. [MEDIUM/inconsistency] Invoice stored breakdown omits rush/premium-takedown fees, so Subtotal − Discount + Tax ≠ Total on the customer-facing invoice
- **File:** src/lib/invoices.ts:99-118 (computeInvoiceTotals) + src/app/admin/invoices/[id]/page.tsx:164-197
- **Evidence:** computeInvoiceTotals only maps subtotal (subtotalBeforeDiscount), discount (discountAmount + earlyInstallDiscountAmount), tax, and total. The pricing engine's total INCLUDES rushFeeAmount + takedownAmount (pricingEngine.ts:643-649: taxableAmount = subtotalAfterDiscount + rushFeeAmount + takedownAmount; total = taxableAmount + taxAmount). Those fee lines are dropped from the invoice breakdown. The invoice detail page renders Subtotal / Discount / Tax / Total as a summing itemized ledger (page.tsx:166-182).
- **Impact:** For any order with a rush-install fee or premium takedown, the operator/customer sees Total that does not equal Subtotal − Discount + Tax (the fee amount is silently missing). During the Aug–Oct parallel test against Jobber, invoice totals will visibly fail to reconcile line-by-line, undermining trust in the replacement and causing reconciliation disputes. The load-bearing total/balance are correct — this is a display/breakdown fidelity bug, not a money-movement bug.
- **Fix:** Add a fees field to InvoiceTotals/InvoicePricingInput (rushFeeAmount + takedownAmount) and render a 'Fees' line, OR fold fees into the displayed subtotal, so the shown breakdown reconciles to total.

### B5. [HIGH/broken-step] changes_requested → sent 'resend' is a no-op: quote stays stuck, customer never re-notified
- **File:** src/app/api/quotes/[id]/send/route.ts:151-159
- **Evidence:** The send route short-circuits on `if (quote.quote_sent_at && !isGhlRetry) return { alreadySent:true }` (line 152), BEFORE the status write (`status:'sent'`, line 190) and before any SMS/email. request-changes/route.ts sets `status:'changes_requested'` but leaves `quote_sent_at` intact (line 129). pipelineActions.ts explicitly offers 'edit + resend' for changes_requested (case 'changes_requested': a.push(...sendActions()), line 55-56) and PipelineActionsMenu.run posts /send with a channel body and NO ?retryGhl (line 10-14). So a real resend of a changes_requested quote returns alreadySent, never moves the quote back to 'sent', and never re-messages the customer.
- **Impact:** Core recovery loop is dead: after a customer requests changes, staff edit the quote and click 'Send email + text' — nothing is delivered and the quote reads 'changes_requested' forever. deriveStatus() keeps returning changes_requested (persisted branch status wins, quoteStatus.ts:91). The only escape is the customer directly re-approving (which itself bypasses the state machine) or declining. During Aug–Oct parallel testing this silently strands every change-request deal.
- **Fix:** In the send route, treat a changes_requested resend as a real send: when the persisted status is 'changes_requested' (or add an explicit `?resend`/status check), fall through to re-stamp status:'sent' and re-run messaging instead of short-circuiting on quote_sent_at. Add a test for the changes_requested→sent resend path (currently only 'already-sent short-circuits' and 'changes_requested offers resend' are tested, in isolation).

### B6. [HIGH/bug] Valor balance webhook can resurrect a CANCELLED invoice to 'paid' (no cancelled guard)
- **File:** src/app/api/integrations/valor/webhook/route.ts:485-522
- **Evidence:** handleBalancePayment() only early-returns on `invoice.status === 'paid'` (line 486); it never checks for 'cancelled'. The settle write is a raw `.update({status:'paid', balance:0, ...}).neq('status','paid')` (lines 507-517) — a cancelled invoice has status='cancelled' ≠ 'paid', so the .neq claim passes and flips cancelled → paid, bypassing invoiceStatus.canTransition (cancelled is terminal). The word 'cancelled' does not appear anywhere in the webhook route.
- **Impact:** Real sequence in the testing window: staff send a customer the pay-balance link, then cancel the booking (jobs/[id]/cancel sets invoice→cancelled). A late-arriving or Valor-retried balance webhook (Valor retries up to 3×) then un-cancels the invoice back to paid and closes the job, corrupting the money state after a manual refund may already be underway. pay-balance/route.ts guards cancelled (line 72), but the webhook is the actual settler and Valor fires independently of that guard.
- **Fix:** In handleBalancePayment add `if (invoice.status === 'cancelled') return NextResponse.json({ ok:true, ignored:'invoice-cancelled' })` before the amount check, and/or make the atomic claim `.eq('status', invoice.status)` / `.in('status',['draft','awaiting_payment'])` instead of `.neq('status','paid')` so a cancelled invoice can never be claimed.

### B7. [HIGH/bug] Cancelled booked orders still count as booked revenue and fill the 'Booked · deposit paid' bucket on the dashboard
- **File:** src/lib/dashboard/queries.ts:22-26 + src/lib/dashboard/workflowBoard.ts:63-75 + src/lib/dashboard/metrics.ts:35-42
- **Evidence:** DASHBOARD_QUOTES_SELECT does NOT select the persisted `status` column (nor viewed_at). deriveStatus (quoteStatus.ts:90-97) only returns a terminal status like 'cancelled' when q.status is present; with status unselected it falls through to deposit_paid_at→'booked'. The cancel route (api/jobs/[id]/cancel/route.ts:78) sets status='cancelled' but leaves customer_approved_at AND deposit_paid_at set. metrics.ts sums bookedRevenue for every row with customer_approved_at. grep confirms no dashboard file references cancelled/declined/lost/changes_requested.
- **Impact:** A booked deal that gets cancelled (job/invoice/quote all →cancelled) keeps showing in the dashboard 'Booked · deposit paid' count and its $ value, and in lifetime booked revenue — overstating revenue and the pipeline. During the parallel test any cancellation makes the tool's numbers diverge from Jobber, undermining the comparison the whole Aug–Oct trial is for.
- **Fix:** Add `status` (and viewed_at) to DASHBOARD_QUOTES_SELECT + DashboardQuote, and exclude/segregate terminal statuses (cancelled/declined/lost) in computeWorkflowBoard and metrics.ts booked calcs (e.g. skip rows whose deriveStatus is a terminal branch).

### B8. [MEDIUM/broken-step] 'Edit + resend' for a changes_requested quote is a silent no-op — the send route short-circuits as alreadySent and never re-messages or returns the quote to 'sent'
- **File:** src/app/api/quotes/[id]/send/route.ts:151-159 + src/lib/pipeline/pipelineActions.ts:55-57 + src/app/api/quotes/[id]/request-changes/route.ts:129
- **Evidence:** request-changes writes only { status: 'changes_requested' }, leaving quote_sent_at set. pipelineActions offers the send actions for the 'changes_requested' case. The send route: `if (quote.quote_sent_at && !isGhlRetry) return { alreadySent:true }` — so with quote_sent_at already set, a normal (non-retryGhl) resend sends no SMS/email and does not rewrite status back to 'sent'.
- **Impact:** After a customer requests changes, the operator edits the quote and clicks 'Send email/text' from the Options menu expecting the customer to get the updated quote. Instead nothing is sent, the customer is never re-notified, and the quote is stuck reading 'changes_requested'. This is a core loop in the parallel-test workflow.
- **Fix:** Have request-changes clear quote_sent_at (or set a resend flag), or make the send route treat a changes_requested quote as a fresh send (re-stamp status='sent' + re-message) rather than short-circuiting on quote_sent_at.

### B9. [MEDIUM/broken-step] A booked quote whose auto job-create failed is a dead-end in the ops console — no menu action offers to (re)create the job
- **File:** src/lib/pipeline/pipelineActions.ts:61-77 + src/app/api/integrations/valor/webhook/route.ts:298-303
- **Evidence:** The webhook books the quote (deposit_paid_at + status='booked') then calls createJobFromQuote as BEST-EFFORT inside try/catch — a throw is logged and swallowed. In pipelineActions, the 'booked' case gates every real action on `if (job && ...)`; with job===null only the Details action is returned. The recovery path DOES exist in convert-to-job (route.ts:82-84 calls createJobFromQuote in the alreadyBooked branch), but pipelineActions only offers 'convert-to-job' for status 'approved', never 'booked'.
- **Impact:** If job auto-creation fails (transient DB error, missing job_number seq, etc.) after a real deposit is taken, the order is booked with no job and no invoice, and the operator has no button to recover it — the deal silently falls out of the Jobs pipeline. The comment even says 'a missing job can be reconciled later' but there is no reconcile action.
- **Fix:** In pipelineActions, when quoteStatus==='booked' && depositPaid && !job, offer a 'Create job' action (POST convert-to-job, which is idempotent and recovers the job), or add an explicit reconcile endpoint.

### B10. [LOW/bug] Amend invoice re-sync writes invoice status directly without a canTransition guard and re-reads neither invoice nor job, so a concurrent settle can be clobbered
- **File:** src/app/api/quotes/[id]/amend/route.ts:120-121, 195-223
- **Evidence:** The invoice + its status are read ONCE at the top (job=getJobByQuote, invoice=getInvoiceByJob) before the amendments concurrency re-read (lines 161-174 only re-read approval_snapshot, not the invoice). The re-sync then does a bare `sb.from('invoices').update({...status: reconciledStatus})` bypassing setInvoiceStatus/canTransition. If the balance webhook or mark-paid settles the invoice to 'paid' between the read and this write, the amend overwrites it back to a stale 'awaiting_payment'/'draft' with recomputed balance.
- **Impact:** A race between an operator amend and a customer balance payment can silently un-pay an invoice (status flipped off 'paid', balance reset), producing a double-collection risk or a lost payment record. Low likelihood but it moves money-state, and the amend path advertises itself as the careful/delicate one.
- **Fix:** Re-read the invoice immediately before the re-sync and gate the status change through canTransition (or an atomic conditional update keyed on the expected current status), matching the atomic-claim pattern used elsewhere.

### B11. [CRITICAL/broken-step] "Request changes → staff edit → resend" loop is dead-ended — a changes_requested quote can never be re-sent
- **File:** src/app/api/quotes/[id]/send/route.ts:152 (short-circuit); src/app/api/quotes/[id]/request-changes/route.ts:129; src/lib/quotes.ts:202-240 (updateQuote); src/lib/quoteStatus.ts:124
- **Evidence:** request-changes sets status='changes_requested'. quoteStatus.ts ALLOWED_TRANSITIONS permits changes_requested → sent, and pipelineActions.ts offers 'Send (resend)' for that state. BUT the send route is idempotent on quote_sent_at: line 152 `if (quote.quote_sent_at && !isGhlRetry) return {alreadySent:true}` — once sent, quote_sent_at is non-null forever, so a resend does nothing (no status re-stamp, no customer SMS/email). updateQuote (quotes.ts:215) never touches status or quote_sent_at. grep confirms NO route ever executes changes_requested→sent. send/route.test.ts has 0 tests referencing changes_requested/resend.
- **Impact:** During the Aug–Oct parallel test, any customer who clicks 'Request changes' puts the quote permanently in changes_requested. Staff edit it in the builder, hit Send, get a silent 'alreadySent' no-op — the customer is never re-notified and the quote is stuck in a non-forward state forever. This is a LOCKED SPEC §4.1 decision and an explicit Phase-1 'done when' criterion ('a customer can request changes (note → staff edit → resend)'), and it is non-functional.
- **Fix:** Add a resend path: either (a) have request-changes / the edit-save flow null out quote_sent_at (and set status back to 'draft' or 'changes_requested'), or (b) give the send route an explicit resend branch that, when status==='changes_requested', re-stamps quote_sent_at + status='sent' and re-messages the customer. Wire it to the pipelineActions 'Send (resend)' action and add a route test for the changes_requested→sent transition.

## Gaps
### G1. [HIGH/gap] Portal loader never selects status/decline_reason, so declined / changes_requested / cancelled quotes still render the full approve+pay UI to the customer
- **File:** src/lib/portal/loader.ts:47-53
- **Evidence:** loadPortalQuote selects only ...customer_approved_at, approval_snapshot, deposit_paid_at, is_test — not `status` or `decline_reason`. The PortalQuote shape therefore carries no lifecycle-branch state. The portal decides what to show purely from approved/paid timestamps, so a quote in declined/changes_requested/cancelled looks identical to a fresh sent quote and keeps showing Approve/Pay. Combined with the un-gated /approve above, the decline is invisible and reversible from the customer side.
- **Impact:** A customer who declined (or whose quote staff cancelled) sees no acknowledgement and can re-approve/pay against a dead quote; staff get a booking + deposit on an order they closed. The 'declined is terminal' contract (decline/route.ts:18-25) is not enforced anywhere the customer can see or act.
- **Fix:** Select `status` (and decline_reason) in loadPortalQuote, surface it on PortalQuote, and have the portal render a terminal/branch state (declined/cancelled → read-only 'this quote is closed'; changes_requested → 'we're revising your quote') instead of the approve/pay controls. This also backstops the /approve gate fix.

### G3. [HIGH/gap] Abandoned deposit checkout permanently blocks the operator's manual convert-to-job (no way to clear valor_order_ref)
- **File:** src/app/api/quotes/[id]/convert-to-job/route.ts:106-115 ; src/app/api/quotes/[id]/pay/route.ts:112-120
- **Evidence:** /pay stamps quotes.valor_order_ref (`q<hex>`) BEFORE redirecting the customer to the hosted page (pay/route.ts:117-120). convert-to-job then refuses to manually book ANY quote whose valor_order_ref is non-null: `if (quote.valor_order_ref) return 409 code:'payment-in-flight'` (convert-to-job/route.ts:106-115). A grep for valor_order_ref shows it is NEVER cleared anywhere in src/ — nothing resets it on checkout failure/cancel/timeout. simulate-deposit refuses non-test quotes, so it is not an escape hatch either.
- **Impact:** During the Aug–Oct parallel test, customers will routinely open the deposit checkout and abandon it (close the tab, card declines, change their mind). That quote's valor_order_ref stays set forever, so the operator can NEVER manually convert it to a job (cash/check/terminal deposit) — every attempt returns 'A customer card payment is in progress' 409. The only way to book it becomes a real Valor webhook that never arrives. Operators hit a permanent dead-end on a normal, expected customer behavior.
- **Fix:** Give the guard an escape hatch: (a) only treat a checkout as 'in flight' within a TTL (e.g. compare against a checkout-started timestamp / updated_at and allow manual booking after N minutes), or (b) add an explicit operator 'clear pending payment / reconcile' action that nulls valor_order_ref after they confirm nothing settled in Valor, or (c) accept a `force: true` on convert-to-job that the UI surfaces after showing the warning. The webhook already dedupes on deposit_paid_at IS NULL, so a stale-ref override is safe as long as the operator confirms non-settlement.

### G4. [MEDIUM/gap] Deposit webhook books on ANY approved amount and never verifies it against the intended deposit (asymmetric with the balance branch)
- **File:** src/app/api/integrations/valor/webhook/route.ts:245-276,344-349
- **Evidence:** The balance branch explicitly rejects an underpayment: `if (paid == null || paid + 0.01 < invoice.balance) → underpaid` (webhook/route.ts:495-501). The DEPOSIT branch has no equivalent check — once event.approved is true (response_code '00') it stamps deposit_paid_at + status='booked' with NO comparison of event.amountUsd against the intended deposit (quotes.deposit_amount_usd set by /pay at pay/route.ts:119). It also does NOT write deposit_amount_usd from the confirmed amount, so createInvoiceFromJob later applies the INTENDED deposit (invoices.ts:381-383 reads quotes.deposit_amount_usd), not what Valor actually captured.
- **Impact:** Any signed, approved transaction on this EPI that maps to the quote's order ref books it and applies the intended deposit to the invoice — even if Valor captured a different amount (partial approval, a portal surcharge/tax re-applied despite ignore_surcharge_calc, or a mis-set amount). The invoice's deposit_applied and therefore the customer's balance would be wrong, and no log/flag surfaces the mismatch. The balance path guards this exact class of error; the deposit path does not.
- **Fix:** In the deposit branch, after parsing, compare event.amountUsd to the expected deposit (quotes.deposit_amount_usd) with a 1-cent tolerance and either (a) refuse/flag a mismatch like the balance branch does, or (b) at minimum persist the ACTUAL confirmed amount into deposit_amount_usd (so the invoice bills the real balance) and log any divergence for reconciliation.

### G8. [MEDIUM/gap] Deposit webhook does not verify the paid amount against the intended deposit (asymmetric with the balance branch)
- **File:** src/app/api/integrations/valor/webhook/route.ts:260-349
- **Evidence:** The deposit branch books on any approved ('00') txn with a matching order ref and never compares event.amountUsd to the intended deposit (quotes.deposit_amount_usd, stamped by pay/route.ts:117-120). event.amountUsd is used only for the receipt display (line 344-349). - **Impact:** If Valor ever confirms an approved txn for less than the intended deposit (stale hosted page, an amount edited on Valor's side, a partial capture), the quote is still booked as fully deposited and the later invoice under-computes the balance by the shortfall — the customer is under-billed and nothing flags it. ### G12. [LOW/untested] complete route's zero-balance auto-settle only fires for a 'draft' invoice, so a re-completed job with a zeroed non-draft invoice never closes
