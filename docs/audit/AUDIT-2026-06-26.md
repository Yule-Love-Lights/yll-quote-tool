## Executive Summary

The pricing engine and the core send→approve→snapshot flow are basically sound and well-tested. The tool is **not production-safe for peak season as-is**, and the reason is overwhelmingly **one theme: there is effectively no authentication on the operator surface.** Two findings are outright CRITICAL — the `/customers` list and detail pages are *server components with no auth* that render every customer's name/address/phone/email to any anonymous visitor, and the GoHighLevel contact-search API is unauthenticated, allowing full CRM PII enumeration. Behind them sits a wall of HIGH/MEDIUM issues that share the same root cause: operator pages gate only their data *calls* (a single static `x-admin-secret` in sessionStorage) not their *render*, and most write APIs (settings, training, corrections, uploads, designs, quote) have no auth at all — so the AI training corpus can be poisoned, global business settings changed, and quote rows created/re-priced anonymously. Compounding it: RLS is disabled on every table, there is no creator/actor audit trail, customer property photos and PII are retained indefinitely, and customer-facing pages have no error/not-found boundary (a not-found quote or a Supabase blip shows a bare framework error page). Quote-accuracy risks are narrower but real: garland section-count silently falls back to 1 (under-billing long runs), the approve route trusts client-sent dollar totals without recompute, and scene→line-item linking can mis-map after a post-calculate edit. Fix the two CRITICALs and the auth cluster before season; the rest is first-week/first-month hardening.

### Customers list page server-renders all customers' PII unauthenticated

- **Severity:** CRITICAL · **verdict:** confirmed
- **Issue:** Same root cause as the detail page, but worse blast radius: this `force-dynamic` (line 9) server component fetches up to 500 quotes via the service-role client (listQuotesForDashboard, line 49, which uses getSupabaseServiceClient bypassing RLS — see queries.ts lines 12-13) and renders EVERY customer's name, email-or-phone (CustomerRow line 20, 38), quote count, and booked spend (lines 40-43) to any anonymous visitor of /customers. - **Exact fix:** Introduce a server-side auth perimeter for operator pages. Preferred: create a NEW src/middleware.ts (it does not currently exist) with a matcher covering /customers, /customers/:id, /admin/:path*, /settings, /quote/:path*, /training, /insights, /inventory that verifies an operator session (httpOnly signed cookie) and redirects unauthenticated requests to a login route before any SSR runs. Note this is one shared auth-perimeter fix for all operator pages, not a per-page patch; the client sessionStorage 'x-admin-secret' is not a server gate and must be replaced/supplemented by a server-validated session.

### Unauthenticated CRM contact search enables full customer-PII enumeration

- **Severity:** CRITICAL · **verdict:** confirmed
- **Issue:** GET /api/integrations/highlevel/contacts?q=<query> has NO admin auth. It checks isHighLevelConfigured() and applies only a 30/min per-IP rate limit (line 31), then proxies a live GoHighLevel contact search (searchContacts, line 43) and returns CrmContact records containing full name, email, phone, and street address (address1/city/state/postalCode — see toCrmContact in src/lib/integrations/highlevel.ts:307-324). The `raw` field is stripped (line 45) but every PII field a customer cares about is still returned. Any anonymous internet user can hit this endpoint and, with a 2-char minimum query (line 38), walk the alphabet ('aa','ab',...,'sm','jo',...) to enumerate the entire Yule Love Lights customer database — names, emails, phones, home addresses — 30 requests/minute per IP, trivially parallelized across IPs. This is a direct mass-PII breach of the CRM through the quote tool.
- **Root cause —** `src/app/api/integrations/highlevel/contacts/route.ts:21-47`: The route was written as an internal autocomplete for the admin new-quote page but was never gated behind the shared x-admin-secret check that other admin routes use (see checkAdminSecret in src/app/api/quotes/route.ts:11-21). The per-IP in-memory rate limit is a quota guard, not authentication, and is bypassable via x-forwarded-for spoofing (src/lib/rateLimit.ts:18-23 trusts the first XFF value).
- **Exact fix:** Add the same admin gate the quotes routes use. At the top of GET, after the isHighLevelConfigured() check (before the rate limit), insert: `const expected = process.env.ADMIN_SECRET; if (!expected) return NextResponse.json({ error: 'ADMIN_SECRET not configured on server' }, { status: 503 }); if (req.headers.get('x-admin-secret') !== expected) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });`. Keep the rate limit as defense-in-depth. Better: extract checkAdminSecret from quotes/route.ts into a shared module (e.g. src/lib/adminAuth.ts) and reuse it here and in the other currently-unauthenticated highlevel routes (attach, and any sibling that proxies CRM data). Longer term, since the secret is read client-side from sessionStorage and forwarded as a static header, operator routes need real session auth rather than a shared static secret; and validate/strip x-forwarded-for in getIp so the rate limit can't be trivially bypassed.
- **Verifier evidence:** src/app/api/integrations/highlevel/contacts/route.ts:21-58 (no x-admin-secret check; only isHighLevelConfigured + rate limit; raw stripped at :45; 2-char min at :38); src/lib/integrations/highlevel.ts:76-86 (searchContacts → live GHL /contacts/?query call); src/lib/integrations/highlevel.ts:307-324 (toCrmContact returns email/phone/address1/city/state/postalCode); src/lib/rateLimit.ts:18-23 (getIp trusts first unvalidated x-forwarded-for → spoofable); src/app/api/quotes/route.ts:11-21 (checkAdminSecret gate that this route lacks); glob **/middleware.ts → no files (no global auth gate)

### Customer detail page leaks CRM PII to anonymous visitors (no auth)

- **Issue:** This is a `force-dynamic` (line 11) server component with NO auth check of any kind — no middleware (none exists in the repo), no route-group layout gate (the /customers tree has no layout.tsx; root layout.tsx has no gate), no admin-secret header, no session check. ### Operator pages have no server-side auth — full staff UI renders to anonymous visitors

- **Severity:** HIGH · **verdict:** confirmed
- **Issue:** Every operator page is a 'use client' component with no server-side gate. Anyone who navigates to /admin/quotes, /settings, /quote/new, /training, etc. gets the full staff UI shell rendered. The admin secret is only requested when a DELETE is attempted (admin/quotes/page.tsx:65-66 calls getAdminSecret on the action). Read endpoints those pages call (e.g. GET /api/quotes at admin/quotes:36, GET /api/training, GET /api/settings, GET /api/corrections) have NO auth, so an anonymous visitor sees the real quote list, customer names, training data, and business settings — material PII/operational exposure (§9). The page surface also reveals internal workflow, field names, and endpoints to an attacker.
- **Root cause —** `src/app/admin/quotes/page.tsx:1-20 (client component; secret only gates the data calls, not the render); same model for /settings, /quote/new, /training, /customers, /insights, /inventory`: Auth was bolted onto individual destructive data calls, not onto navigation. Client-only pages can't enforce auth before render, and no middleware redirects unauthenticated users away from operator routes.
- **Exact fix:** Add a src/middleware.ts (or per-route-group server layout) that requires an authenticated admin session cookie for the operator route groups (/admin, /settings, /quote, /training, /customers, /insights, /inventory) and redirects to a login page otherwise. Critically, also gate the read APIs the pages call — GET /api/quotes, GET /api/settings, GET /api/training, GET /api/corrections, etc. — behind the same admin check (reuse/extend the existing checkAdminSecret or a session check), so customer PII and business settings are unreachable even if a page bundle is loaded by an anonymous visitor. The data-API gating is the load-bearing fix; the page-render gate alone is insufficient.
- **Verifier evidence:** No middleware.ts (Glob **/middleware.ts → none). src/app/admin/quotes/page.tsx:1 ('use client'), :36 (fetch('/api/quotes') with no auth), :54-63 (secret only in adminFetch), :65-69 (only DELETE uses it). src/app/api/quotes/route.ts:23-29 (GET unauthenticated) vs :39 (auth only on DELETE). src/lib/quotes.ts:19-34 (service-role client selects customer PII). src/app/api/settings/route.ts:11-22 (GET unauthenticated).

### save-correction persists fully unvalidated body straight into the AI training corpus

- **Severity:** HIGH · **verdict:** confirmed
- **Issue:** POST /api/save-correction does `body = (await req.json()) as CorrectionPayload` and passes it directly to saveCorrection() with ZERO field validation. The route has no admin auth (per the audit brief). saveCorrection (corrections.ts:63-89) then inserts payload.correctedSantasFootage / correctedGingerbreadFootage / correctedWinterWonderlandFootage and all the *Lines / *Detections arrays verbatim into photo_corrections. Nothing checks that the numbers are finite/non-negative, that difficulty is one of easy|medium|hard, or that the arrays/base64 are bounded. A client can persist NaN/Infinity/negative footage, a 50MB photo_base64, or arbitrarily large arrays. These rows are read back by getRecentCorrections() and fed into the few-shot prompt that seeds every future AI house analysis (photoAnalysis.ts), so poisoned/garbage corrections silently degrade pricing accuracy across all quotes — a data-integrity blast radius well beyond one row.
- **Root cause —** `src/app/api/save-correction/route.ts:15-26 (route) + src/lib/corrections.ts:56-89 (sink)`: The route trusts the request body via a TypeScript cast (`as CorrectionPayload`), which is erased at runtime and performs no validation; the lib layer also assumes a well-formed payload.
- **Exact fix:** In src/app/api/save-correction/route.ts, validate the parsed body before calling saveCorrection. Reuse the pattern from src/app/api/quote/route.ts: add `function isFiniteNonNeg(v: unknown): v is number { return typeof v === 'number' && Number.isFinite(v) && v >= 0; }`. Then: require typeof body.photoBase64 === 'string' with a length cap (e.g. <= ~11M chars ≈ 8MB decoded) and typeof body.photoMediaType === 'string' starting with 'image/'; require isFiniteNonNeg for correctedSantasFootage, correctedGingerbreadFootage, and (when present) correctedWinterWonderlandFootage; constrain correctedSantasDifficulty/correctedGingerbreadDifficulty to ['easy','medium','hard']; require each supplied *Lines / *Detections field to be Array.isArray with a length cap (e.g. <= 500); cap notes length (e.g. <= 2000 chars). Return 400 on any failure. Optionally also gate the route behind the same x-admin-secret check used by the other admin write routes, since corrections are a staff-only training action. Keep saveCorrection's lib-layer assumptions unchanged once the route guarantees a well-formed payload.
- **Verifier evidence:** src/app/api/save-correction/route.ts:15-22 (cast, no validation), :7-13 (only a Supabase-config guard, no auth); src/lib/corrections.ts:63-89 (verbatim insert into photo_corrections), :98-113 (getRecentCorrections reads them back); src/lib/fewShot.ts:123 + 133-136 (corrections fed into the few-shot prompt for every analysis); src/app/api/quote/route.ts:11-81 (the existing per-field validation the fix should mirror); no src/middleware.ts exists (Glob returned no files).

- **Severity:** HIGH (finder said CRITICAL; verifier adjusted) · **verdict:** adjusted
- **Issue:** POST /api/integrations/highlevel/attach has NO admin auth — only config checks and a 20/min per-IP rate limit (line 63). ### Insights/close-ratio metrics silently degrade to wrong numbers on query failure or 500-row truncation

- **Severity:** MEDIUM · **verdict:** confirmed
- **Issue:** listQuotesForDashboard() logs the Supabase error to console and returns an empty array on failure (queries.ts:24-28). The Insights page (insights/page.tsx) and KPI/close-ratio math (metrics.ts, insights.ts) then compute over [] and render '—' or $0 / 0% with NO error banner — an operator reading 'Close ratio —' or 'Total booked $0' cannot distinguish 'genuinely no data' from 'the query broke'. Separately, the page requests only listQuotesForDashboard(500) (insights/page.tsx:23): once the business exceeds 500 lifetime quotes, every headline metric (close ratio, avg job value, total booked) is computed on only the newest 500 rows and silently understates/distorts lifetime figures with no truncation notice.
