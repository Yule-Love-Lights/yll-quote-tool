# Full-Tool Audit: AI Quote Tool (2026-07-06)

Whole-tool report-only adversarial audit across money, data, portal, auth, AI, correctness, and cleanup. Report only: no code changed, no PRs opened.

## Executive summary

- **Severity counts:** 1 CRITICAL, 4 HIGH, 10 MEDIUM, 8 LOW (23 confirmed bugs), plus 10 suggestions and dead-code items.
- **Top 3 must-fix:**
  - **Event portal double-bills the front footage** (`src/lib/event/packages.ts:43`): the event package bundles both mutually-exclusive rooflines, so the front footage is billed twice and the inflated total is frozen into the approval snapshot and deposit charge.
  - **Tax-override write clobbers a concurrent balance payment** (`src/lib/invoices.ts:693`): no status compare-and-swap, so an override landing during a Valor settlement resurrects a paid invoice with a phantom balance and risks a double charge.
  - **home.works resend bills the full quote, not the approved selection** (`src/app/api/integrations/homeworks/send/route.ts:141`): a resend after a partial approval sends the supplier a signature/payment request for more money than the customer agreed to.

## Findings

### [CRITICAL] Event portal package bundles both mutually-exclusive roofline options, double-billing the front footage
- **File:** `src/lib/event/packages.ts:43`
- **What's wrong:** `derivePackagesEvent` builds the single "Event Lighting" package as `includedItemIds: lineItems.map(li => li.id)` and sums every line into the card subtotal. For an event quote with both front footage (`santasFootage`) and ridge/sides footage (`gingerbreadFootage`), the adapter replaces the one billed roofline with two mutually-exclusive options: `roofline-santas` (front only) and `roofline-gingerbread` (front + ridge + sides). Gingerbread already contains the front, but the event package includes both. `computeInitialSelection` seeds both as selected, and the roofline mutual-exclusion only fires on a toggle click, never on the seed. The approve route's server recompute sums both ids into the authoritative snapshot total. Holiday's `derivePackages` explicitly drops the Santa's option via `excludeRooflineId`; permanent has no rooflines; only event lacks this exclusion.
- **Failure scenario:** Staff build an event quote with `santasFootage=100ft` ($500) and `gingerbreadFootage=50ft` ($250). Rooflines become santas=$500 and gingerbread=$750 (front + ridge/sides). The "Event Lighting" card totals $500 + $750 = $1,250 pre-tax instead of $750: the front 100ft is billed twice. The portal opens with both rooflines pre-selected and "Included". The customer clicks Approve without touching toggles; the approve route recomputes the same double-count, freezes ~$544 of phantom charge into the approval snapshot, and the Valor deposit charges 50% of the inflated total. The invoice later bills the same overstated total.
- **Suggested fix:** In `derivePackagesEvent`, drop `roofline-santas` from the bundle when `roofline-gingerbread` is present (mirror `derivePackages`'s `excludeRooflineId`). Defense in depth: make `computeInitialSelection` and the approve recompute enforce the roofline group's mutual exclusion (keep only the recommended roofline when both ids are selected).
- **Verdict:** CONFIRMED.

### [HIGH] setInvoiceTaxOverride's final write has no status compare-and-swap
- **File:** `src/lib/invoices.ts:693`
- **What's wrong:** `setInvoiceTaxOverride` reads the invoice, checks `status !== 'paid'`, does further async reads (source quote), then UPDATEs subtotal/tax/total/balance/status by `.eq('id', id)` only, with no status precondition. Every sibling money write uses compare-and-swap: `markInvoicePaidManually`'s `.neq` guards, the balance webhook's `.in(['draft','awaiting_payment'])` claim, `setInvoiceStatus`'s `.eq(status)` CAS. A settlement landing between this read and write is silently clobbered.
- **Failure scenario:** An invoice is `awaiting_payment` with a $500 balance. The customer pays via the Valor balance pay-link (webhook atomically sets status=`paid`, balance=0, `paid_at`) at the same moment the operator toggles the tax override on `/admin/invoices`. The override's read happened pre-settlement so it passes the "paid" pre-check; its unguarded UPDATE then writes status back to `awaiting_payment` with a recomputed positive balance over the just-recorded payment. The invoice shows a balance outstanding on an already-collected order (`paid_at` still stamped, tripping the reconcile "inconsistent" flag) and staff can charge the customer a second time.
- **Suggested fix:** Re-read the invoice status immediately before the final write and make it a CAS: add `.eq('status', <freshly-read-status>)` (or exclude paid/cancelled via `.in`), and abort/return null on 0 rows matched, mirroring `setInvoiceStatus`'s pattern.
- **Verdict:** CONFIRMED. (Low-probability window, but a genuine TOCTOU that is guarded everywhere else in the same file.)

### [HIGH] home.works resend bills the FULL quote total, not the customer-approved selection
- **File:** `src/app/api/integrations/homeworks/send/route.ts:141`
- **What's wrong:** `totalUsd` is computed as `r?.total ?? quote.total ?? 0` (the full engine-priced result), while the route explicitly supports resending an already-approved quote (reads `snapshot.customerSelection.activeName`; has a `force=true` resend path guarded only by an idempotency check, not approval state). The `ApprovalSnapshotPartial` cast narrows the snapshot to `{customerSelection?: {activeName?, packageId?}}`, dropping `currentTotalUsd`, the exact field `resolveAgreedTotal()` was built to consult so invoices bill the agreed (possibly partial-selection) total. This route was never updated to use it.
- **Failure scenario:** A customer approves after deselecting line items or picking a cheaper roofline tier (package B/C), so `approval_snapshot.customerSelection.currentTotalUsd` is now less than `result.total`. An operator later re-sends the quote to home.works (`?force=true`, or a first send after approval). The Zapier payload's `totalUsd`/`subtotalAfterDiscountUsd` reflect the full un-selected pricing, so home.works generates a signature/payment request for more money than the customer approved.
- **Suggested fix:** Import `resolveAgreedTotal` from `@/lib/agreedTotal` and use it (or the same precedence) to compute `totalUsd`/the line-item breakdown from the agreed total when `approval_snapshot` is present, mirroring how `src/lib/invoices.ts` derives `agreedTotal` for invoice creation.
- **Verdict:** CONFIRMED. (Blast radius bounded by whether home.works is live and whether operators re-send after a partial approval; it is a signature/estimate step, not an instant card charge.)

### [HIGH] Approve route honors a POSTed early-install discount even when "hide early-install discounts" is on
- **File:** `src/app/api/quotes/[id]/approve/route.ts:461`
- **What's wrong:** The server-side recompute derives the discount from client-supplied `installTiming` (`discountRate = installDiscountRate(installTiming)`) without consulting `appSettings.portal.hideEarlyInstallDiscounts`, even though `getAppSettings()` is already awaited. The portal contract is that when the setting is on, the Sep/Oct picker is hidden and the discount forced off. The route already forge-proofs rush/takedown/installTiming for permanent/event (`noHolidayFees`), but the seasonal hide flag has no server enforcement for holiday quotes.
- **Failure scenario:** Staff flip Settings → Customer Portal → "hide early-install discounts" on (season passed). A customer (or anyone holding the quote UUID) POSTs `/api/quotes/{id}/approve` with `installTiming:'september'` via devtools/curl; the server recomputes with 15% off, freezes the discounted total/deposit into the authoritative snapshot, `/pay` charges the reduced deposit, and the invoice bills the under-priced snapshot: a 10-15% under-bill of the whole order. Softer non-forged path: a portal tab opened before the flag flip submits a then-visible discount after staff turned it off.
- **Suggested fix:** In the approve route, force `installTiming` to `'none'` (and `installDiscountUsd` to 0) when `appSettings.portal.hideEarlyInstallDiscounts` is true, alongside the existing `noHolidayFees` forcing.
- **Verdict:** CONFIRMED. (Primary path is a forged/out-of-band request, so an enforcement gap rather than a passive happy-path under-bill, with the softer stale-tab race also real.)

### [HIGH] Approved (locked) portal renders the default/recommended selection and prices, not the frozen approved selection
- **File:** `src/app/portal/[quoteId]/page.tsx:241`
- **What's wrong:** When a quote is approved, the portal re-renders with `locked=true` but seeds `SelectionProvider` from the same defaults an unapproved quote uses: `initialSelectedItemIds` from the staff-recommendation D package, `initialPackageId` from `pickInitialPackageId`, rush/takedown from staff defaults. Nothing restores the approval snapshot's selectedItemIds/packageId/rush/takedown (`PortalApproval` only carries `selectedItemCount`). Only `installTiming` is restored. Meanwhile `WhatsIncluded`'s locked copy claims "This is your booked quote" and `InteractiveHero` labels the card "Your selected package".
- **Failure scenario:** A customer approves a holiday quote at $2,100 (garland off, rush added) where the recommendation was $2,400. They re-open the portal link: the hero shows $2,400, `WhatsIncluded` shows garland with a checked "Included" badge and rush absent, the tie-out shows a total/deposit different from what they signed, and the copy asserts "This is your booked quote". The authoritative-looking display contradicts what they actually approved. No wrong charge (`/pay` and the invoice use the frozen snapshot), but the customer-facing display is wrong.
- **Suggested fix:** When `quote.approval` exists, seed `SelectionProvider` from the frozen snapshot: expose selectedItemIds, packageId, rushSelected, takedownSelected on `PortalApproval` and prefer them over the recommendation/default seeds, mirroring `installTiming`.
- **Verdict:** CONFIRMED. (Display-only, but on a booked quote where the customer diverged from the staff recommendation the hero price, tie-out, package highlight, and Included badges all contradict what was signed.)

### [MEDIUM] Amend flow is deadlocked for booked orders: the reprice lock blocks the only path that can change the amend delta
- **File:** `src/app/api/quotes/[id]/amend/route.ts:155`
- **What's wrong:** The amend route derives the new total purely from the stored pricing result: `newTotal = agreedTotal + (quote.result.total - approval_snapshot.pricing.total)`, and 409s "no-change" when the delta is under a cent. But `quote.result`'s only write path is `/api/quote → updateQuote`, whose reprice lock returns 409 "quote-locked" for any booked order. The two guards point at each other: once a deposit is paid, `quote.result.total` can never diverge from `snapshot.pricing.total`, so every post-booking amend attempt 409s forever.
- **Failure scenario:** A booked customer asks to add a $400 wreath after paying the deposit. The operator clicks "Amend order", edits, clicks Calculate → 409 "This order is booked... Use the amend flow". The operator goes to the job page, clicks "Record amendment" → 409 "No price change detected — edit the order in the builder (Calculate) first". Loop. The extra $400 can never be added through the app; staff eat the revenue or hand-edit the database.
- **Suggested fix:** Give `/api/quote` an explicit amend mode for booked orders (operator-only) that updates result/inputs without touching lifecycle, immediately followed by the amend record; or have the amend route accept validated new inputs and re-price internally (same engine dispatch) so the delta source exists again.
- **Verdict:** CONFIRMED. (An approved-but-not-yet-booked window can still reprice, which is the narrow escape hatch and why this is MEDIUM, not HIGH; it does not cover the common approve+pay-then-change case.)

### [MEDIUM] Customer merge .or() filter interpolates unsanitized name/email keys
- **File:** `src/lib/customers.ts:221`
- **What's wrong:** `findOrCreateCustomer`'s secondary-identity search builds a PostgREST `.or()` filter with `match_key.in.(${secondaryKeys.join(',')})`. `secondaryKeys` embed free-text values (`name:<lowercased name>`, `email:<email>`) with no sanitization; `safeOrValue()` only guards the raw column conditions, not these key strings. A comma or paren in a name corrupts the in-list, the `.or()` error is silently swallowed, and the merge is skipped.
- **Failure scenario:** A quote saved with `customer_name` "Acme, Inc. (East)" and no HL/email match → the `.or()` becomes `match_key.in.(name:acme, inc. (east))` → PostgREST parse error → silently ignored → dedupe skipped → a duplicate customers row is created (the exact split the secondary search was built to prevent). The finding also raises a more severe crafted-name injection that could overwrite an unrelated customer's identity; that escalation is PLAUSIBLE but not demonstrable, since the likely outcome of any injected reserved char is the parse-error/silent-swallow path.
- **Suggested fix:** Apply the same `safeOrValue()`-style allowlist to each secondary key before interpolation (skip keys containing `,` `(` `)` or other reserved chars), or replace the string-built `.or()` with separate parameterized `.in()`/`.eq()` queries per condition.
- **Verdict:** CONFIRMED (the broken-dedupe/duplicate-row half; the identity-overwrite escalation is PLAUSIBLE only).

### [MEDIUM] On-hand stock adjustments are absolute-set writes from stale snapshots
- **File:** `src/lib/inventory/orders.ts:181`
- **What's wrong:** `receiveOrder` reads the on-hand table once, then writes `current + line.qty` per SKU via `upsertOnHand`, an absolute set, not an increment. `prepareJobMaterials` has the same shape with a wider window: it computes each deduction's "after" from a snapshot taken before the atomic claim, then writes the absolute `d.after`. The per-order/per-job claims only prevent double-processing the same order/job; nothing serializes two different writers on the same SKU, so last write wins and one delta vanishes.
- **Failure scenario:** On-hand for C9-500 is 100. Job A (needs 30) and Job B (needs 40) are prepped near-simultaneously; both snapshots read 100. A writes 70, B writes 60 → final 60 instead of 30: 30 units of phantom stock. `buildSupplierPurchaseOrder` then subtracts the inflated on-hand and under-orders by 30, so materials are short at install. A `receiveOrder` increment racing a prep decrement loses received stock the same way.
- **Suggested fix:** Make stock changes atomic deltas: a Postgres RPC (`update inventory_on_hand set on_hand_qty = greatest(0, on_hand_qty + $delta) where sku = $sku`), or an `updated_at` optimistic-retry guard like `designs.updateExtraPhotosAtomic`.
- **Verdict:** CONFIRMED. (Needs near-simultaneous same-SKU writers, which is why MEDIUM; likelihood-at-scale is a severity lever, not a refutation.)

### [MEDIUM] /api/quote update branch fails open when the existing-row read errors
- **File:** `src/app/api/quote/route.ts:372`
- **What's wrong:** `getQuoteRaw` returns null for both a missing row and a Supabase read error, and the route can't tell them apart. With a valid `quoteId` but `existing===null`, three guards silently disappear: the reprice-locked check, the rate-drift guard (permRates/eventRates falls through to LIVE settings instead of the quote's frozen snapshot), and the stored-service-type fallback. `updateQuote` then still executes and, if the row exists, overwrites inputs/result/total.
- **Failure scenario:** An operator opens a booked permanent quote's edit page and clicks Calculate at the moment `getQuoteRaw`'s select blips (transient Supabase error). Instead of the intended 409 "quote-locked", the quote is re-priced from LIVE `permanentRates` (raised since booking) and its result/total silently rewritten with no amendment trail, no invoice re-sync, no re-consent. A `serviceType`-omitting body additionally re-prices through the holiday engine.
- **Suggested fix:** Distinguish error from missing in `getQuoteRaw` (throw or return a sentinel); in the route, 503 on a read error and 404 when `isUpdate` but no row, instead of proceeding to `updateQuote`.
- **Verdict:** CONFIRMED. (Trigger is narrow, a transient read error on this one select at the moment a booked quote is repriced, matching MEDIUM.)

### [MEDIUM] Entire /api/inventory operator surface omits the per-route requireOperator() gate
- **File:** `src/app/api/inventory/purchase-order/route.ts:26`
- **What's wrong:** Every operator API outside inventory calls `requireOperator()` as a documented second layer behind the middleware perimeter. The ~14-route `/api/inventory/*` cluster has no per-route gate; it relies solely on the `src/proxy.ts` middleware perimeter. These are side-effectful, PII-bearing routes: POST `/api/inventory/purchase-order` emails a real supplier order; POST `/api/inventory/jobs/[id]/email-order` sends an internal order email with customer name and address; PUT/DELETE `/api/inventory/on-hand` and POST/PATCH `/api/inventory/catalog` write stock levels and SKUs. Tracked as W7-013 (Naldo lane), still unfixed.
- **Failure scenario:** With `AUTH_GATE_ENABLED` not flipped (the documented current pre-go-live state), the middleware is a no-op, so on live prod an unauthenticated POST to `/api/inventory/purchase-order` triggers a real supplier PO email, and PUT `/api/inventory/on-hand` corrupts inventory counts, with no auth. After go-live these routes remain single-layered while the rest of the operator surface is double-layered, so any future perimeter/matcher/allowlist regression re-exposes the most side-effectful routes with no backstop.
- **Suggested fix:** Add `const denied = await requireOperator(); if (denied) return denied;` to the top of every non-cron `/api/inventory/*` handler (the two Vercel-cron routes keep their `CRON_SECRET` gate instead).
- **Verdict:** CONFIRMED. (`requireOperator()` is itself dormant until go-live, so MEDIUM, but the defense-in-depth gap on the most dangerous routes is real.)

### [MEDIUM] home.works send has no atomic dedupe claim: concurrent requests can double-send the estimate
- **File:** `src/app/api/integrations/homeworks/send/route.ts:95`
- **What's wrong:** The idempotency guard is a plain read-then-check: the route SELECTs the quote, checks `quote.homeworks_sent_at`, calls the external Zapier webhook, and only after that external send succeeds writes `homeworks_sent_at` back. Unlike every money-path route (approve/pay/webhook/convert-to-job use `.is('column', null)` as an atomic UPDATE claim before firing side effects), there is no equivalent guard: two concurrent POSTs for the same quoteId can both read `homeworks_sent_at:null` before either write lands.
- **Failure scenario:** An operator double-clicks "Send to home.works" (slow network, or two tabs), or a client retry fires after a timeout the first request actually completed. Both requests pass the `!quote.homeworks_sent_at` check concurrently, both call `sendQuoteToHomeworks`, and home.works creates two real estimates/contracts for the same order.
- **Suggested fix:** Add an atomic pre-claim before calling `sendQuoteToHomeworks`: `UPDATE quotes SET homeworks_sending_at = now() WHERE id = :id AND homeworks_sent_at IS NULL AND (homeworks_sending_at IS NULL OR homeworks_sending_at < now() - interval)`, select the row, and only proceed if the claim won. Finalize `homeworks_sent_at` on success; clear the sending marker on failure. (The sibling `homeworks/signed` route was already hardened this exact way.)
- **Verdict:** CONFIRMED. (Real supplier-facing double-send within a concurrency/retry window, not on the happy path.)

### [MEDIUM] With checkout OFF, an approved-then-cancelled/declined quote still shows the full "You're booked" state
- **File:** `src/app/portal/[quoteId]/page.tsx:220`
- **What's wrong:** `isBooked = checkoutEnabled || isTest ? isPaid : isApproved`. With the Valor checkout flag off (today's placeholder default), approval alone makes `isBooked` true. The page-level dead-quote gate skips itself whenever `quote.approval` exists, and `StickyBottomBar`'s dead-approval branch only fires when `depositFlow` is true, so in checkout-off a quote that staff cancel or decline after customer approval (both legal transitions) still renders the `BookedBanner`, the booked sticky bar, and the `/approved` celebration page.
- **Failure scenario:** Checkout flag off. Customer approves the placeholder flow, then backs out by phone; staff mark the quote declined (or cancel it). The customer re-opens their portal link: the top banner says "You're booked — approved June 3. We'll reach out to collect your 50% deposit", the sticky bar says "You're booked", and "View confirmation" shows the celebration page, for an order staff already killed. The customer reasonably believes the install is still on.
- **Suggested fix:** In the checkout-off branch require the quote to still be actionable (or paid) to read as booked, e.g. `isBooked = (checkoutEnabled || isTest) ? isPaid : (isApproved && (isPaid || isPortalActionable(quote.quoteStatus)))`; show the neutral closed notice otherwise; keep genuinely paid quotes on the booked view.

### [MEDIUM] analyze-photo accepts image types the analyzer rejects (e.g. HEIC), surfacing a permanent misleading "temporarily unavailable" error
- **File:** `src/app/api/analyze-photo/route.ts:43`
- **What's wrong:** The route validates only `mediaType.startsWith('image/')`, but `analyzePhoto` throws for anything outside jpeg/png/gif/webp. The throw is swallowed by `runAnalyzeWithFewShot`'s catch, which returns `ANALYZER_UNAVAILABLE_MESSAGE` ("temporarily unavailable... click Analyze again in a few minutes"). ### [MEDIUM] Reference-library prompt-cache breakpoint sits after the per-request dynamic system suffix, so it almost never hits
- **File:** `src/lib/photoAnalysis.ts:685`
- **What's wrong:** The end of the reference-images message is marked with `cache_control`, but an Anthropic cache lookup requires the entire prefix (tools → system → messages) up to the breakpoint to be byte-identical. The dynamic system suffix sits between the cached static prompt and the reference block and varies per request: `satelliteNote` embeds `feetPerPixel.toFixed(4)` (unique per address), `styleNote` embeds the hint, `examplesNote` embeds retrieval counts. On the primary analyze-address flow the suffix differs for every address, so the reference-block cache write (~6 images plus labels, thousands of tokens at 1.25x) is billed on virtually every call and read back on almost none. The static-prompt breakpoint still works; only the second is defeated.
- **Failure scenario:** Two quotes for different addresses within the 5-minute TTL: call 1 writes the reference-block cache segment at 1.25x; call 2's `satelliteNote` has a different ft/px string, the prefix hash differs, the cache misses, and the same images are written again at 1.25x. Net effect is a standing ~25% surcharge on the reference-image tokens instead of the intended ~90% saving.
- **Suggested fix:** Move the per-request notes (satellite/style/examples/bias) out of the `system` array into the final user message so `system` + reference block form a byte-stable cached prefix; keep `cache_control` where it is.
- **Verdict:** CONFIRMED. (Cost-inefficiency, money-adjacent, not a customer-billing correctness bug.)

### [LOW] Manual percentage discount rounds to whole dollars in the engine but to cents on the portal/approve path
- **File:** `src/lib/pricing/pricingEngine.ts:845`
- **What's wrong:** `computeTotalsTail` computes a percentage discount as `Math.round(subtotalBeforeDiscount * amount)`, whole dollars (the event engine copies this). The portal live price and the approve route's authoritative recompute both use `priceSelection`, which rounds the same discount to cents. For any % discount whose exact value isn't a whole dollar, the engine total written to `quotes.total` (and shown in the builder, admin list, dashboards, and the `resolveAgreedTotal` legacy fallback) differs by up to ~54 cents (with tax knock-on) from the total the customer approves and is billed.
- **Failure scenario:** Staff apply a 15% discount to a $1,235 item subtotal. Engine: `Math.round(185.25)=$185`, stored total shown in the builder. Portal/approve: $185.25, agreed total frozen and billed. The operator quotes one figure verbally while the portal charges a few cents different, a standing sub-dollar discrepancy on every %-discounted order. Billing stays correct (the agreed snapshot governs); the drift is operator-facing plus a stale legacy-fallback total.
- **Suggested fix:** Change the engine's percentage-discount rounding to cents (`Math.round(subtotal * amount * 100) / 100`) in both `computeTotalsTail` and the event tail so it matches `priceSelection`, or centralize one rounding rule shared by both paths.
- **Verdict:** CONFIRMED. (Sub-dollar, customer billed the correct snapshot figure, so genuinely LOW.)
